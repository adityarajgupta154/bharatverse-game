Aru Move / Walk / Run Kyu Nahi Karta — Poora Gap Analysis

Date: 30 August 2026 · Scope: artifacts/bharatverse ka har folder & file · Language: Hinglish
Ek line mein jawab: Aru ke paas movement ka poora system (keyboard + touch + collision + camera) project mein maujood hai aur kaam karta hai — lekin woh sirf minigame screen ke andar (jaise Naali Paheli) chalta hai. Memory Map aur Village screens par Aru ek entity hi nahi hai — wahan woh ya to painting ke andar baked hai ya render hi nahi hota. Isliye wahan chalna, daudna, ghoomna technically impossible hai — yeh bug nahi, architecture ka design gap hai. Aur "Run" (daudna) feature poore project mein kahin bana hi nahi — sirf ek fixed walk speed hai.

1. Sabse Pehle: Game 3 Alag "Duniya" Mein Bana Hai

Analysis mein sabse important finding yeh hai ki BharatVerse ek single game-engine app nahi hai. Yeh teen bilkul alag technologies se bane screens ka collection hai, aur Aru ka "wajood" teeno mein alag hai:

Layer 1 — Memory Map (Hub)

MOVEMENT IMPOSSIBLE

Ek static PNG image (hub-reference.png, 2.57 MB). Aru, gates, paths — sab artwork ke andar baked hain. Aru yahan koi element hi nahi hai jo hil sake — woh wallpaper ka hissa hai. Upar sirf invisible click-buttons (hotspots) hain.

Layer 2 — Village World (Mohenjo-Daro)

ARU RENDER HI NAHI HOTA

Ek static painting (village-sindhu.jpg, 1024×1536) jo React (HTML DOM) mein dikhai jaati hai. Isme Aru ka sprite kahin draw hi nahi hota. Aap painting ko sirf pan/scroll karte ho; buildings & NPCs click/hover hotspots hain. Point-and-click adventure pattern.

Layer 3 — Minigame (Canvas Engine)

MOVEMENT WORKS ✓

Asli 2D game engine — <canvas> par 60fps loop. Yahan Aru ek living entity hai: position, speed 190px/s, collision, camera follow, WASD/arrows + mobile joystick. Naali Paheli isi par bana hai aur fully verified hai.

Gap ka core yahi hai: jo movement engine Layer 3 mein hai, woh Layer 1 & 2 se connect hi nahi kiya gaya. Village/Hub screens DOM-based "menu screens" jaise bane hain, game world jaise nahi.

3. Jahan Movement Kaam Karta Hai — Engine Ka Anatomy

Yeh samajhna zaroori hai ki problem "movement code kharab hai" wali nahi hai. Engine solid hai. src/game/engine/ mein 5 files hain:

FileKaamStatus
input.ts (131 lines)Keyboard (WASD/arrows/E/Space/Enter) + touch joystick + action queue. Listeners window par lagte hain — canvas focus ki zaroorat nahi. Diagonal movement normalized (1.0 speed).Working
movement.ts (61 lines)Collision-aware movement: axis-separated AABB, quarter-tile substeps (tunneling se bachav), wall-sliding. Har frame: dx = dir.x × speed × dt.Working
camera.ts (23 lines)Camera Aru ko follow karta hai, level ke edges par clamp.Working
loop.ts (65 lines)Fixed 60Hz update + render loop (requestAnimationFrame + accumulator).Working
sprites.ts (62 lines)Image loading helpers.Working

Movement kab chalta hai, kab nahi (minigame ke andar bhi)

  • Intro card dikh raha ho ("Shuru Karo" button) → movement OFF. Sirf button click ke baad ON hota hai (GameScreen.tsx:68, 214–226). Agar aapko lagta hai "game khula par Aru nahi chal raha" — 90% chance yeh hai ki intro card par "▶ SHURU KARO" abhi dabaya nahi gaya.
  • Pause (Esc) → OFF, dobara Esc → ON.
  • Jeetne ke baad (win card) → OFF (by design).
  • Baaki har waqt: keyboard se turant chalta hai — yeh e2e testing + deterministic simulation dono se verified hai.

4. Root Cause: Exact 5 Gaps

GAP #1 — Village screen mein "player entity layer" hai hi nahi

NodeWorldScreen.tsx ek painting-viewer hai: static <img> + pan/scroll + click hotspots. Isme na Aru ka sprite hai, na position state, na input-to-movement wiring, na collision. Aru wahan "chal nahi pata" nahi — Aru wahan hai hi nahi.

GAP #2 — Hub map par Aru artwork mein baked hai

MapStage.tsx:16–25 ka comment khud kehta hai: map, gates, rings, paths aur Aru — sab reference art ke andar baked hain. Ek painted pixel ko keyboard se nahi hilaya ja sakta. Isko walkable banane ke liye Aru ko art se nikaal kar ek alag layer/sprite banana padega.

GAP #3 — Walkability/collision data sirf minigame levels ke paas hai

Engine ko chalne ke liye chahiye: "kaunsi jagah walkable hai, kaunsi blocked". Yeh data (tile grid + isWalkable) sirf drain-puzzle-scene.ts / demo-scene.ts ke andar hai. Village painting (village-sindhu.jpg) ke liye koi collision map authored nahi hai — buildings/paani/gharon ke aage rukne ka data exist nahi karta.

GAP #4 — "Run/Sprint" feature kahin implement nahi hai

Poore codebase mein ek hi speed hai: PLAYER_SPEED = 190 px/sec (walk). Koi Shift-to-run, dash, stamina, speed multiplier — kuch nahi (input.ts mein sirf movement + action keys defined hain). Isliye Aru minigame mein bhi sirf walk karta hai, run kabhi nahi.

GAP #5 — Game "isometric" hai hi nahi (art ka illusion hai)

Engine pure top-down orthogonal hai: square 64px tiles, seedha x = col×64, y = row×64 par draw (engine/types.ts:3–7). Koi diamond projection, skew, ya depth-sorting math nahi hai. Village painting perspective/isometric-jaisi dikhti hai (artist ne waise banayi hai), par engine flat hai. Isliye "isometric view hone ke baad bhi" wali expectation art se aa rahi hai, code se nahi.

6. Yeh Aisa Kyu Bana? (Context)

Yeh koi accident nahi tha — PRD ke phases ke hisaab se hub aur village point-and-click exploration screens ke roop mein design hue (painted art + hotspots), aur "asli gameplay" minigames ke andar canvas engine par gaya. Dono approaches apni jagah sahi hain; gap tab dikhta hai jab expectation ho ki Aru village mein bhi RPG ki tarah ghoome. Woh feature abhi tak kisi phase mein banaya hi nahi gaya — na iska sprite layer hai, na collision data, na input wiring us screen par.

7. Kya Karna Hoga — Fix Roadmap

Option A (Recommended): Village ko walkable canvas world banao

Existing engine ko reuse karke NodeWorldScreen ko canvas scene mein badla jaye:

  • Background: wahi village-sindhu.jpg painting canvas par draw hogi (art change nahi karna).
  • Aru sprite layer: aru-sprite-cut.png painting ke upar, engine ke moveActor se WASD/arrows + joystick movement, camera follow (tall art 1024×1536 ke liye vertical camera — abhi jo manual scroll hai woh automatic ho jayega).
  • Collision mask: painting ke upar ek walkable-grid author karna padega (gharon, paani, walls block) — yeh is option ka sabse bada naya kaam hai.
  • Building entry: click ki jagah proximity — building ke paas jao, "E — Andar jao" prompt (Naali Paheli ke pick-prompt jaisa hi pattern).
  • NPC dialogue: hover ki jagah paas jaane par bubble (proximity trigger) — mobile par bhi natural ho jayega.
  • Solvability guard: wahi headless sim pattern (debugState() + verify script) — taaki har building tak pahunchna hamesha possible rahe.

Effort: Medium — engine ready hai; naya kaam = collision mask + triggers + camera tuning + testing. Ek focused task ka scope.

Option B: DOM-based movement (quick hack)

Aru ko HTML <img> bana kar CSS transform se hilana. Jaldi ban jayega par collision, camera, performance aur mobile handling messy ho jaati hai — engine already hai to iska koi faayda nahi. Not recommended.

Choti additions (kisi bhi option ke saath)

  • Run/Sprint: Shift hold = speed ×1.6 — input.ts mein ek modifier + scenes mein speed param. Chhota kaam, minigames + village dono mein milega. Mobile ke liye joystick ke edge par sprint.
  • Hub (Memory Map): walkable banana low-value hai — yeh conceptual map hai, click-based hi theek hai. Zyada se zyada Aru ka animated marker add ho sakta hai jo selected region par khada ho.
  • True isometric: recommend NAHI — poori art + engine rework maangta hai (diamond tiles, depth sorting). Aapki painted art already premium lagti hai.

8. Common Confusions — Clear Karte Hain

AssumptionReality
"Movement ka code toota hua hai / bug hai"Nahi — engine sahi hai. Naali Paheli mein movement automated e2e testing + deterministic simulation dono se proven hai. Gap sirf yeh hai ki village/hub screens engine use hi nahi karte.
"Keyboard focus / click issue hoga"Nahi — key listeners window-level hain, canvas focus ki zaroorat nahi. Minigame mein sirf "▶ Shuru Karo" dabana zaroori hai (intro ke dauraan input jaan-boojh kar OFF hai).
"Game isometric engine par bana hai"Nahi — engine top-down orthogonal (square grid) hai; isometric feel sirf painted art ka hai.
"Run kaam nahi kar raha"Run feature exist hi nahi karta — implement karna hoga (chhota kaam).
"Village mein Aru dikh raha hai par hil nahi raha"Village mein jo Aru "dikhta" hai woh sirf hub art mein baked figure hai; village painting mein to Aru render bhi nahi hota. Hilne ke liye pehle uska sprite layer banana padega.

9. Final Verdict

Kya gap hai? Ek hi sentence mein: movement engine aur exploration screens ke beech ka pul (bridge) kabhi banaya nahi gaya. Engine (input + collision + camera + loop) production-quality hai aur Naali Paheli mein proven hai. Village/Hub screens static art + click hotspots par bane hain — unme player entity, collision data, aur input wiring teeno missing hain (GAP #1–#3). Run feature kahin nahi hai (GAP #4), aur isometric sirf art ka illusion hai (GAP #5).

Recommended fix: Option A — village ko existing engine par walkable world banana (collision mask + proximity triggers), saath mein Shift-sprint. Isse game "menu jaisa" nahi, "RPG jaisa" feel karega — bina art dobara banaye.
